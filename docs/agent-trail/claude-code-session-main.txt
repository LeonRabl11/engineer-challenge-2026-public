● The inbox search is handled server-side. Here's exactly what it does.

  Endpoint

  GET /feedback in server/src/index.ts:77. The client calls it from
  web/src/api.ts:19 (fetchInbox), passing the search box value as the q query
  parameter:
  GET /feedback?page=<n>&status=<all|open|resolved>&q=<search>
  The value is read at index.ts:80: const search = ((req.query.q as string) || 
  '').trim().

  Which columns are matched

  When q is non-empty, the search matches three columns (index.ts:88–92):
  1. feedback.message — the feedback message text
  2. customers.name — the customer's name (via subquery on the customers table)
  3. customers.email — the customer's email (via the same subquery)

  A row matches if the message contains the term OR the row's customer_id
  belongs to a customer whose name or email contains the term. All matching is
  LIKE '%term%' (substring, case-insensitive by SQLite's default for ASCII).

  Exact SQL

  The search adds this filter fragment (index.ts:89–91):
  (message LIKE '%<q>%' OR customer_id IN (SELECT id FROM customers WHERE name
  LIKE '%<q>%' OR email LIKE '%<q>%'))
  It's combined with the status filter (status = '<status>', added only when
  status ≠ all, index.ts:85–86) using AND, then assembled into the final query
  (index.ts:97):
  SELECT * FROM feedback
  WHERE (message LIKE '%<q>%' OR customer_id IN (SELECT id FROM customers WHERE
  name LIKE '%<q>%' OR email LIKE '%<q>%'))
  ORDER BY created_at DESC
  LIMIT 10 OFFSET <offset>

  Concrete example for q=refund + status=resolved (page 1):
  SELECT * FROM feedback
  WHERE status = 'resolved' AND (message LIKE '%refund%' OR customer_id IN
  (SELECT id FROM customers WHERE name LIKE '%refund%' OR email LIKE
  '%refund%'))
  ORDER BY created_at DESC
  LIMIT 10 OFFSET 10

  The q and status values are interpolated directly into the SQL string
  (template literals at index.ts:86 and index.ts:90), not passed as
